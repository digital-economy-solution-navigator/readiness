# AI Solution Readiness Assessment (AISRA) Framework
### Version 3.0 — Solution Fit Edition

---

## Overview

The **AI Solution Readiness Assessment (AISRA)** is a structured tool that helps UNIDO project managers determine whether — and how — candidate AI solutions can successfully land in a specific country or sector context.

AISRA is built on a core insight: **a solution that works well in one context can fail in another, not because the technology is wrong, but because the conditions are different.** AISRA makes those conditions visible and actionable.

### What AISRA is designed to do

A project manager typically enters an AISRA process with **2–3 candidate solutions** in mind. AISRA helps them answer three questions for each candidate:

1. **Can it work here?** — Is the country or sector context compatible with what this solution requires?
2. **What would need to be true?** — If there are gaps, what conditions must be met first?
3. **Which solution fits best?** — Across candidates, which has the strongest fit profile?

### How it is conducted

AISRA assessments combine **desk review** (country diagnostics, sector reports, existing data inventories) with **stakeholder consultations** (field interviews and workshops with government counterparts, CoE partners, and end users). Neither alone is sufficient — desk review surfaces structural conditions; consultations surface operational realities.

---

## The Assessment Structure

AISRA evaluates each candidate solution against four **Fit Dimensions** — the factors most likely to determine whether a solution translates successfully across contexts:

| # | Fit Dimension | Core Question |
|---|---------------|---------------|
| 1 | **Technical Infrastructure & Connectivity** | Does the physical and digital infrastructure exist to run this solution? |
| 2 | **Data Availability & Quality** | Is the data this solution depends on available, reliable, and accessible? |
| 3 | **Institutional Capacity & Ownership** | Is there an institution with the mandate, resources, and will to own this solution? |
| 4 | **Local Skills & Workforce Readiness** | Are there people who can operate, maintain, and use this solution? |

Each dimension contains a set of **diagnostic criteria**. Each criterion is answered as:

| Response | Meaning |
|----------|---------|
| **Yes** | Condition is met in the current context |
| **Partial** | Condition is partially met; a gap exists but is addressable |
| **No** | Condition is not met; a significant barrier exists |

Criteria are classified as either **Critical** or **Enabling**:

- **Critical criteria** — If answered No, the solution faces a fundamental barrier. A No on a Critical criterion triggers an Adapt or No-Go recommendation.
- **Enabling criteria** — If answered No or Partial, a gap exists but can be addressed through targeted investment or pre-conditions. These inform a Go with Conditions recommendation.

## The Four Fit Dimensions & Diagnostic Criteria

### Dimension 1 — Technical Infrastructure & Connectivity

*Does the physical and digital environment support how this solution operates?*

| # | Criterion | Type | Desk Review Indicators | Consultation Questions |
|---|-----------|------|----------------------|----------------------|
| 1.1 | The solution's minimum connectivity requirements (e.g., mobile data, broadband, offline-capable) are met in the deployment area | Critical | National/regional connectivity coverage data; ITU reports | What is typical connectivity like for frontline users in this sector? |
| 1.2 | End-user devices (smartphones, tablets, sensors, etc.) required by the solution are available or procurable | Critical | Device penetration data; procurement feasibility | What devices do field staff and end users currently have access to? |
| 1.3 | Power supply is sufficiently reliable for the solution's operational requirements | Enabling | Electrification rates; grid stability data | Are there power outages or supply issues that affect digital tools in this area? |
| 1.4 | Existing IT systems (ERP, MIS, databases) that the solution must integrate with are digitised and accessible | Enabling | Systems inventory from government counterparts | What systems are currently in use, and how are they managed? |

---

### Dimension 2 — Data Availability & Quality

*Is the data this solution needs present, trustworthy, and usable?*

| # | Criterion | Type | Desk Review Indicators | Consultation Questions |
|---|-----------|------|----------------------|----------------------|
| 2.1 | The primary data inputs required by this solution (e.g., sensor data, transaction records, registry data) are being collected | Critical | Sector data inventories; national statistics; prior assessments | What data is currently collected in this sector, and by whom? |
| 2.2 | Data is collected at sufficient frequency and granularity for the solution's use case | Critical | Data collection protocols; reporting cadences | How often is data updated, and at what level of detail? |
| 2.3 | Data quality is sufficiently reliable (consistent, complete, accurate) for the solution to produce trustworthy outputs | Critical | Data audit reports; prior data quality findings | Are there known gaps, inconsistencies, or quality issues in the data? |
| 2.4 | Data is accessible in a format compatible with the solution (digital, structured, via API, etc.) | Enabling | Data format and storage documentation | Is data held in paper records, spreadsheets, or a system? Who controls access? |
| 2.5 | Data sharing arrangements between institutions required by the solution are legally and practically feasible | Enabling | Data sharing agreements; legal frameworks | Are there restrictions on sharing data across ministries or agencies? |

---

### Dimension 3 — Institutional Capacity & Ownership

*Is there an institution with the mandate, resources, and commitment to own and sustain this solution?*

| # | Criterion | Type | Desk Review Indicators | Consultation Questions |
|---|-----------|------|----------------------|----------------------|
| 3.1 | A lead institution exists with a clear mandate covering the solution's functional domain | Critical | Organisational charts; legal mandates; sector strategies | Which institution would be responsible for this type of system? |
| 3.2 | The lead institution has demonstrated commitment to digital transformation or similar initiatives | Critical | Prior project track record; digital strategy documents | Has this institution led or participated in digital projects before? What was the outcome? |
| 3.3 | The lead institution has sufficient operational budget and staffing to sustain the solution post-deployment | Enabling | Budget allocations; staffing data | What is the institution's current capacity to operate a digital system long-term? |
| 3.4 | Coordination mechanisms exist between the institutions the solution requires to collaborate | Enabling | Inter-agency agreements; coordination body existence | How do the relevant institutions currently work together? Are there coordination structures in place? |
| 3.5 | Political will and senior leadership buy-in for the solution exists within the lead institution | Enabling | Policy statements; engagement history | Is there visible support from senior leadership for this type of initiative? |

---

### Dimension 4 — Local Skills & Workforce Readiness

*Are there people who can operate, maintain, and use this solution effectively?*

| # | Criterion | Type | Desk Review Indicators | Consultation Questions |
|---|-----------|------|----------------------|----------------------|
| 4.1 | Sufficient digital literacy exists among the end users who will interact with the solution daily | Critical | Education statistics; prior training assessments; digital literacy surveys | What is the typical digital skill level of the people who would use this tool day-to-day? |
| 4.2 | Technical staff capable of administering and maintaining the solution (IT, data management) are available locally | Critical | ICT workforce data; institutional staffing profiles | Does the lead institution have IT or data staff in-house, or would this need to be contracted? |
| 4.3 | Training capacity exists to onboard users and build long-term operational capability | Enabling | Training infrastructure; CoE capacity; vocational institutions | What training resources — institutions, trainers, programmes — exist in this sector? |
| 4.4 | The solution's interface and workflow are compatible with how users currently work (language, process, literacy) | Enabling | User journey documentation; language/literacy data | Are there language, process, or workflow factors that could affect how easily users adopt this tool? |

## Generating the Fit Recommendation

Once all criteria are assessed for a candidate solution, the response pattern determines the **Fit Recommendation** using the logic below. No numerical scoring is required — the recommendation is driven by the configuration of Critical and Enabling responses.

### Recommendation Logic

| Fit Recommendation | Criteria Pattern | Meaning |
|--------------------|-----------------|---------|
| **✅ Go** | All Critical criteria = Yes; Enabling criteria mostly Yes with minor Partials | Solution is viable in the current context with standard implementation support |
| **⚠️ Go with Conditions** | All Critical criteria = Yes or Partial; some Enabling criteria = No or Partial | Solution is viable but specific gaps must be addressed before or during deployment — document as pre-conditions |
| **🔧 Adapt** | One or more Critical criteria = Partial, or a pattern of Nos across Enabling criteria | Solution requires meaningful localisation or redesign to function in this context — document what must change |
| **🚫 No-Go** | One or more Critical criteria = No | A fundamental barrier exists that cannot be resolved through conditions or adaptation alone — solution is not viable in current context without structural change |

### Escalation Rule

If a **Critical** criterion is answered **Partial**, treat it as a potential No-Go signal and probe further before assigning a final recommendation. A Partial on a Critical criterion means the barrier may be real but not yet fully understood — use the consultation questions to determine whether it is genuinely addressable.

## Conditions & Adaptation Register

For every criterion answered Partial or No, the PM documents a specific entry in the **Conditions & Adaptation Register**. This turns the assessment into an actionable work plan.

| Criterion | Response | Type | Barrier Description | Required Action | Responsible Party | Timing |
|-----------|----------|------|--------------------|-----------------|--------------------|--------|
| *(e.g.)* 2.1 — Primary data inputs being collected | Partial | Critical | Animal movement data collected by DVS but only at provincial level; farm-level data absent | Design a farm-level data capture protocol as a pre-condition to deployment | DVS + UNIDO TC team | Before deployment |
| *(e.g.)* 4.2 — Local technical staff available | No | Critical | No in-house IT staff at lead institution | Embed a UNIDO-supported technical officer for Year 1; build handover plan | Lead institution + UNIDO HR | At project inception |
| *(e.g.)* 3.3 — Operational budget for sustainability | Partial | Enabling | Budget exists but below what is needed for full operations | Include a budget support component in project design | Ministry of Finance + UNIDO | Project design phase |

### Selection Guidance

The preferred solution is typically the one with the **strongest fit recommendation and the fewest Critical-level barriers**. Where two solutions have similar fit profiles, the following secondary factors should guide the final selection:

- **Depth of Conditions Register** — fewer and simpler pre-conditions favour faster deployment
- **CoE delivery capacity** — does a CoE in the network have experience delivering this solution type?
- **Strategic sequencing** — does one solution create the data or institutional foundation the other depends on?
- **Cost of adaptation** — where adaptation is required, is it within project scope and budget?

## Illustrative Application: Zambia Livestock Sector

### Context

Zambia is evaluating three candidate solutions for its national livestock sector transformation programme. The PM has conducted a desk review and two days of stakeholder consultations with DVS (Department of Veterinary Services), MALF, and provincial livestock officers.

**Candidate Solutions:**
- **Solution A** — National Livestock Identification & Traceability System (NLIS)
- **Solution B** — Predictive Early Warning System for disease surveillance (PLEWS), ML-dependent
- **Solution C** — Rule-based disease surveillance dashboard using existing DVS data

---

### Fit Comparison (Zambia)

| Fit Dimension | Criterion | Solution A (NLIS) | Solution B (PLEWS-ML) | Solution C (Dashboard) |
|---------------|-----------|:-----------------:|:--------------------:|:---------------------:|
| **Technical Infrastructure** | 1.1 Connectivity | Partial | No | Yes |
| | 1.2 End-user devices | Partial | Partial | Yes |
| | 1.3 Power supply | Partial | Partial | Partial |
| | 1.4 IT integration | Partial | No | Partial |
| **Data Availability & Quality** | 2.1 Primary data collected | Partial | No | Yes |
| | 2.2 Frequency & granularity | Partial | No | Partial |
| | 2.3 Data quality | Partial | No | Partial |
| | 2.4 Data format compatibility | Partial | No | Yes |
| | 2.5 Data sharing feasibility | Partial | Partial | Yes |
| **Institutional Capacity** | 3.1 Lead institution mandate | Yes | Yes | Yes |
| | 3.2 Institutional commitment | Yes | Partial | Yes |
| | 3.3 Operational sustainability | Partial | No | Partial |
| | 3.4 Coordination mechanisms | Partial | Partial | Partial |
| | 3.5 Leadership buy-in | Yes | Partial | Yes |
| **Local Skills** | 4.1 End-user digital literacy | Partial | No | Partial |
| | 4.2 Local technical staff | Partial | No | Partial |

| | 4.4 Interface compatibility | Partial | No | Yes |
| **Fit Recommendation** | | ⚠️ Go with Conditions | 🚫 No-Go | ⚠️ Go with Conditions |

---

### Preferred Solution

**Solution C (Rule-based Dashboard)** is recommended as the immediate deployment priority. While both A and C qualify as Go with Conditions, Solution C has a lighter conditions register and can be operational on existing DVS data with minimal infrastructure investment.

**Solution A (NLIS)** is recommended as the **next phase** — the data and institutional foundations built through Solution C directly enable NLIS deployment. These two solutions are sequenced, not competing.

**Solution B (PLEWS-ML)** is Not Viable at this time. Multiple Critical criteria are unmet across all four dimensions. The ML-dependent design requires data volumes, quality, and technical staff that do not exist in the current context. It should be revisited once Solutions C and A have been operational for 2–3 years.

---

### Conditions Register (Solution C — Rule-Based Dashboard)

| Criterion | Response | Barrier | Required Action | Timing |
|-----------|----------|---------|-----------------|--------|
| 2.2 — Data frequency | Partial | DVS data reported monthly; dashboard needs weekly updates | Redesign reporting workflow with DVS provincial officers | Before deployment |
| 2.3 — Data quality | Partial | Known inconsistencies in animal count records across provinces | Run a data cleaning exercise and establish QA protocol | Before deployment |
| 4.2 — Local technical staff | Partial | DVS has one IT officer nationally | Embed a UNIDO-supported data officer for Year 1; develop handover plan | At project inception |

## About This Implementation

This repository provides a static web application that presents the AISRA Framework. The implementation consists of:

- **`index.html`** — Page structure, Executive Summary, Framework tab, Case Studies tab
- **`script.js`** — Dimension data, case study data, tab management, and UI rendering
- **`styles.css`** — Supplementary styling (Tailwind CSS loaded via CDN)

To view the framework, open `index.html` in a web browser. No build step or server is required.
